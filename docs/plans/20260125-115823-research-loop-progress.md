# ループ進行保証による再帰上限制御 計画書

**作成日**: 2026-01-25
**目的**: プラン消化後に進捗が止まり無限ループとなる問題を防ぎ、LangGraph の再帰上限エラーを回避する。

---

## 背景
- プラン（検索クエリ列）をすべて処理し終えた場合、現行ロジックでは「検索を行わないまま進捗を増やさない」ため、レビュアーの最低反復条件を満たせず、`max_iterations` にも到達せずにループが継続し、`GraphRecursionError` が発生することがある。

## 対応方針
- プランを使い切ったステップでも進捗を1つ進め、ループを前進させる。一定回数で終了条件に到達するようにする。

## 変更概要
- 研究ステップが枯渇した場合でも「今回のサイクルを1回完了した」とみなし、進捗カウンタを +1 する。
- 空回り（検索0件で進捗のみ加算）発生時に、空回り回数と累積割合を INFO ログに出力し、運用時に上限値を決めやすくする。
- 必要に応じて、進捗だけが進む「空回り」を最小化するための追加終了条件を検討（任意）。

## 具体的変更箇所
- `src/nodes/researcher.py`
  - プラン消費完了分岐で進捗カウンタを +1 して返す。
  - 返却する参照リストは空のまま維持。
  - 空回り発生ごとに、現サイクル番号・累積空回り回数・累積割合（空回り回数/総サイクル数）を INFO ログ出力。

## テスト方針
- プラン件数 0/1 のケースでグラフが停止することを確認する統合テストを追加。
- 複数ステップのプランを途中まで消化した後で枯渇するケースを追加し、空回りが 1 回だけ発生して停止することを確認。
- 進捗カウンタが +1 されることを単体テストで検証（既存テストの期待値に空回り分を加算する）。
- ログ出力に空回り回数・累積割合が含まれることをキャプチャして検証。

### 既存テストの期待値更新手順
1. 進捗カウントを検証するテストを列挙し、プラン枯渇後にループを抜けるケースに +1 を加算する。
2. 空回りを許容しないテストでは、プラン枯渇前で終了するようフィクスチャを調整するか、空回り分の進捗をアサートに反映する。
3. スナップショットテストがある場合は、空回りログが追加されたことによる差分を更新する。

## 想定される影響
- 実際に検索していないサイクルが進捗に含まれるため、統計値がわずかに増えるが、品質への影響は小さい。
- 既存テストで期待する進捗値が変わる場合、アサーションの更新が必要。

## モニタリングと評価指標
- 空回り比率: `empty_cycles / total_cycles`。INFO ログに毎サイクル出力し、初期運用では 5〜10% を超えたら警告扱いとする（最終的な上限は運用で調整）。
- 連続空回り回数: 連続で空回りが発生した回数をログし、再帰上限到達の早期兆候として監視。
- 研究成功率: `successful_search_cycles / total_cycles` を併記し、空回り増加が成功率低下と相関するかを確認。
- ログに記録された空回り回数を集計し、デイリーで空回り比率・連続空回り最大値をダッシュボード化（将来的にメトリクス化を検討）。

### ログフォーマット例（計画レベルの備考）
- INFO `Empty cycle {cycle}/{total}, empty={empty}, ratio={ratio:.2%}, streak={streak}`  
  - `cycle`: 現サイクル番号（1 始まり想定）  
  - `total`: これまで実行した総サイクル数  
  - `empty`: 累積空回り回数  
  - `ratio`: 空回り比率 (`empty/total`)  
  - `streak`: 連続空回り回数

## ロールバック
- 進捗加算を元に戻せば従来挙動に戻るが、無限ループ再発のリスクがあるため非推奨。
